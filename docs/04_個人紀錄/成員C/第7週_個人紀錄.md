## 四、程式理解說明

我選 check_enrollment，因為它是 F2 的核心，主程式與 enroll_course 都靠它判斷能不能加選。

<!-- widths: 20,80 -->
| 項目 | check_enrollment(catalog, student_id, course_id)（campus_planner/enrollment.py） |
| --- | --- |
| Input | 所有資料 catalog、學號、欲加選的課程代號。 |
| Process | 1. 先確認學生與課程都存在，不存在就直接回傳錯誤。<br>2. 檢查是否已選過這門課。<br>3. 把課程時段和學生已選課程、已參加活動比對，並檢查這門課的教室在同時段有沒有被別的課程或活動占用。<br>4. 同一天的連續衝突合併成一筆，全部依星期、節次排序。<br>5. 計算加選後學分是否超過上限，並以實際選修人數判斷是否額滿。<br>6. 所有結果放進 CheckResult；全程不修改資料。 |
| Output | CheckResult：conflicts（時段衝突清單）、errors（學分、額滿、重複等問題）、目前學分、加選後學分、學分上限；conflicts 與 errors 都是空的時 ok 為 True。 |
| Boundary／Error | 1. 學生或課程不存在：回傳錯誤並停止，不做後續檢查。<br>2. 加選後學分剛好等於上限：通過；超過才拒絕（test_credits_exactly_at_limit_allowed）。<br>3. 相鄰節次（第 4 與第 5 節）或同節次不同天不算衝突。<br>4. 剩最後一個名額：可以加選；人數達上限才算額滿。<br>5. 同時衝堂、超學分、額滿：全部列出，不會只回報第一項。 |

### 個人反思與後續規劃

本週的重點是讓 F2「一次列出所有問題」：測試通過容易，但要確認各限制同時發生時不會互相遮蓋，需要專門設計情境。檢視 D 的 F3 時也發現，資料有問題（例如不存在的課程）若被無聲略過，使用者就看不到錯誤，所以 F2 與 F3 都應明確回報異常資料。

下週要做 F5 條件篩選，會先為至少 5 種限制情境寫測試，再實作；也會追蹤 D 對 Code Review 的回應，並在 B 檢視 F2 後處理其意見。
