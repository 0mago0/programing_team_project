# 第 5 週：需求規格整理與最小專案骨架

## 一、專題背景
本專題為六人制 Python 校園選課與活動管理系統，目標是建立一個可管理課程、學生、教室與活動資料的核心系統，並支援衝堂檢查、課表生成、篩選與後續搜尋演算法等功能。

依照作業要求，系統需以命令列介面為主，核心功能必須以可獨立測試的函式實作，且不得依賴全域變數傳遞資料。本週主要聚焦於需求整理和專案初始化，建立統一規格與共用資料模型，為後續 F1～F11 的功能擴充奠定基礎。

## 二、需求整理
本週依照 README.md、docs/assignment.txt、docs/implementation-guide.txt 及 docs/weekly-plan.txt 之內容，整理出本系統的需求範圍與分工規劃。需求分為三類：

### 1. 老師要求
- 系統採用 Python 開發，命令列介面即可。
- 核心功能以可獨立測試的函式實作。
- 不得依賴 input() 或全域變數。
- 使用 Git 管理版本，並可合理運用 AI 協作工具。
- 期中前須完成 F1～F6，後段為 F7～F11。

### 2. 待確認規格
- 時段表示方式：星期 1～7，節次 1～9、a、b、c。
- 課表矩陣定義：7 天 × 12 節次。
- 空堂判定與跨日查詢方式需一致。
- 選課紀錄、資料更新方式與錯誤處理規則需統一。
- 偏好條件與禁止時段需區分為「偏好」與「硬限制」。

### 3. 團隊建議設計
- 以分層式架構開發。
- 使用 dataclass 或相同資料格式定義常用實體資料。
- 通過校內需求規格的共識後，將資料格式與函式介面固定，避免後續各模組失控。

## 三、功能範圍與分工
本專題的主要功能需求包括：
- F1：課程與學生資料管理
- F2：多層次衝堂與選課檢查
- F3：個人課表與空閒時段查詢
- F4：校園活動與教室配置
- F5：多條件課程篩選
- F6：資料儲存與測試
- F7～F11：後續最佳課表、搜尋比較、路徑規劃、事件重規劃與 AI 品質改善

依作業建議，六人分工如下：
- A：組長、整合、F6 儲存載入
- B：F1 資料管理
- C：F2 選課與 F5 篩選
- D：F3 課表與 F4 活動
- E：F7 最佳課表與 F8 搜尋比較
- F：F9 路徑與 F10 動態事件

並且要求每位成員均需參與需求討論、測試與 Code Review，確保團隊知識共享。

## 四、專案架構設計
為了讓後續模組能順利整合，本週建立了最小專案骨架，使用分層架構設計，以便模組獨立驗證並擴充。

核心架構如下：
- main.py：程式入口
- campus_planner/models.py：資料模型
- campus_planner/validation.py：資料驗證與衝突檢查
- campus_planner/data_store.py：資料儲存與載入
- campus_planner/planner.py：示例資料與規劃摘要
- campus_planner/timetable.py：課表矩陣與空閒時段整理
- tests/test_minimal_contract.py：最小測試基線
- data/sample_school_data.json：範例資料

此架構遵循以下設計原則：
- 以純函式為核心，避免依賴全域變數
- 每個模組與函式均有明確輸入與輸出
- 資料格式統一，方便後續各功能模組接續
- 可透過單元測試驗證基本行為

## 五、資料格式與函式介面
本週先統一資料格式與函式介面，避免後續各模組自行定義不一致的資料結構。核心資料包括：
- 課程：代號、名稱、學分、必選修、教師、容量、教室、時段
- 學生：學號、姓名、系級、已選課程、學分上限
- 教室：代號、容量、設備、建築物
- 活動：代號、名稱、日期、時間、預計人數、場地需求

模組中的主要函式包括：
- validate_course()
- validate_student()
- check_time_conflict()
- check_slot_list_conflict()
- evaluate_enrollment()
- save_school_data()
- load_school_data()
- build_weekly_matrix()
- place_course_in_timetable()

藉由這些介面，後續各模組在擴充功能時可以直接沿用相同資料格式與驗證規則，降低整合風險。
